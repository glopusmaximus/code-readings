# Swiss

**[dolthub/swiss](https://github.com/dolthub/swiss)** — 354 lines of Go (+ 55 lines of bit manipulation, 9 lines of generated assembly)

Andy Arthur, DoltHub. 2023.

---

The repository is archived. Go 1.24 adopted Swiss Tables as the implementation behind `map[K]V`, making this library unnecessary. The code that made itself obsolete by being right.

That's the story of this project, but it's not where the reading lives. The reading lives in how 354 lines of Go implement an idea from Google's Abseil C++ library, and specifically in the moment where the abstraction splits: one path through pure bit arithmetic, the other through SSE assembly, both presenting the same interface to 354 lines of map code that never learns which one it's talking to.

## The Split Hash

Every operation begins the same way:

```go
hi, lo := splitHash(m.hash.Hash(key))
```

A 64-bit hash becomes two things. `h1` is the upper 57 bits — it picks which group to start probing. `h2` is the lower 7 bits — it becomes a fingerprint stored in a metadata array alongside the actual keys. The insight is that you've already computed the hash. Throwing away the low bits to pick a bucket wastes information. Keeping them as a per-slot filter means most failed comparisons never touch the keys at all.

The metadata array is `[groupSize]int8`. Each byte is either a 7-bit hash fingerprint (non-negative), `empty` (-128, `0b10000000`), or `tombstone` (-2, `0b11111110`). These sentinel values aren't arbitrary. Empty is the high bit set with everything else clear. Tombstone is the high bit set with other bits set. Every valid h2 has the high bit clear. This means you can distinguish all three categories with bit operations on the raw bytes, no branching required.

## Two Ways to Search Eight Bytes

Here's where the code does something I find genuinely beautiful. The question is: given a metadata array and a target h2 value, which slots match?

On non-amd64 hardware (or with `nosimd` build tag), groups are 8 slots. The metadata fits in a single `uint64`. The match function:

```go
func metaMatchH2(m *metadata, h h2) bitset {
    return hasZeroByte(castUint64(m) ^ (loBits * uint64(h)))
}

func hasZeroByte(x uint64) bitset {
    return bitset(((x - loBits) & ^(x)) & hiBits)
}
```

`loBits` is `0x0101010101010101`. Multiplying it by the target byte broadcasts that byte into all eight positions. XOR with the metadata produces a uint64 where matching positions are zero bytes, non-matching positions are nonzero bytes. Then `hasZeroByte` detects which byte-lanes contain zeros — the classic SWAR trick from Stanford's Bithacks page, discovered independently multiple times since the 1980s.

The trick works because subtracting `0x01` from a zero byte borrows from the high bit, and ANDing with the complement of the original confirms the high bit wasn't already set. The result: a bitset with the high bit of each matching byte set, everything else clear. `nextMatch` finds the lowest set bit with `TrailingZeros64`, clears it, and divides by 8 to get the slot index.

Eight comparisons. No branches. One subtraction, two ANDs, one XOR.

On amd64, groups are 16 slots. The metadata fills a 128-bit SSE register. The match function calls into six instructions of generated assembly:

```asm
MOVD     CX, X0       // load hash byte into low 32 bits of XMM
PXOR     X1, X1       // zero a register
PSHUFB   X1, X0       // broadcast: zero-shuffle copies lowest byte to all 16 positions
MOVOU    (AX), X1     // load 16 metadata bytes from memory
PCMPEQB  X1, X0       // parallel compare: each byte becomes 0xFF if equal, 0x00 if not
PMOVMSKB X0, AX       // extract high bit of each byte into a 16-bit mask
```

Sixteen comparisons. No branches. Six instructions.

The assembly is generated by [Avo](https://github.com/mmcloughlin/avo), a Go library for writing Go assembly in Go. The generator itself (`asm.go`) is twelve lines of Avo calls that produce the `.s` file. The build tag system routes each platform to its implementation. The map code never sees the difference — it calls `metaMatchH2`, gets a `bitset`, iterates with `nextMatch`. The only observable difference is that `groupSize` is 8 on one path and 16 on the other, which means groups hold more elements and the load factor is higher (87.5% vs 87.5%, but over twice as many slots per group).

## The Map Itself

With the matching machinery hidden behind `metaMatchH2` and `metaMatchEmpty`, the map operations are almost readable as pseudocode.

`Get`: hash the key, pick a starting group, probe linearly. Within each group, match the h2 fingerprint against all slots simultaneously. For each match, compare the actual key. If no h2 matches and the group contains an empty slot, the key doesn't exist. If no empty slots, move to the next group.

`Put`: same probe sequence. If you find the key, update it. If you find an empty slot, insert there. If you hit the load limit first, rehash.

`Delete` contains the most interesting comment in the codebase:

```go
// optimization: if |m.ctrl[g]| contains any empty
// metadata bytes, we can physically delete |key|
// rather than placing a tombstone.
// The observation is that any probes into group |g|
// would already be terminated by the existing empty
// slot, and therefore reclaiming slot |s| will not
// cause premature termination of probes into |g|.
```

In open-addressing hash tables, you can't just mark a deleted slot as empty — a later key might have been inserted past that slot during a collision, and marking it empty would make that key unfindable. The standard solution is tombstones: a third state meaning "nothing here, but keep probing." But tombstones accumulate and degrade performance. Swiss Tables probe at group granularity, not slot granularity. If a group already contains an empty slot, probing into that group will always continue to the next slot regardless. So a deletion within that group can use `empty` instead of `tombstone`. This is the kind of optimization that falls out of the design rather than being bolted on — it's a consequence of group-level probing being the primitive.

`rehash` has a similar structural insight: if more than half the occupied slots are dead (tombstones), it rehashes in place rather than growing. The tombstones are the problem, not the capacity.

## The Functions That Aren't There

The `find` method exists but has a comment saying it's "manually inlined into public methods." The commit history confirms this: `7ad77f1 manually inlined find into Has, Get, Put and Delete`. Before that commit, the public methods called `find`. After it, each contains its own copy of the probe loop.

This is a performance decision that costs readability. The four methods share identical probe logic, and the inlining makes them longer without making them clearer. But for a hash table competing with Go's built-in map, function call overhead matters. The compiler might or might not inline a method with multiple loops and branches. Andy Arthur chose not to hope.

The `fastModN` function at the very end of the file is a one-liner with a blog post citation:

```go
// lemire.me/blog/2016/06/27/a-fast-alternative-to-the-modulo-reduction/
func fastModN(x, n uint32) uint32 {
    return uint32((uint64(x) * uint64(n)) >> 32)
}
```

This replaces the modulo operator with a multiplication and shift, avoiding the expensive division instruction. It also means the number of groups doesn't need to be a power of two — a constraint that most hash table implementations accept as given. Swiss Tables don't, and this one function is why.

## What Happened Next

Go 1.24, released February 2025, replaced its native map implementation with Swiss Tables. The Go team's version was informed by this library and others, and by the same Abseil paper. DoltHub archived the repository with a one-line README update and a link to their blog post about the decision.

The commit history tells a complete story in 20 commits: initial implementation, benchmarks, SIMD fallback for ARM, performance inlining, community contributions for edge cases (Clear not zeroing values, fastrand deprecated in Go 1.22), and then archival. No feature creep. No scope expansion. A library that did one thing, proved it was the right thing, and made itself unnecessary.
